# Повторное обучение при деградации

`retrain_on_degradation.py` сравнивает два проверенных отчёта по периодам работы
одной версии модели. При ухудшении он рекомендует повторное обучение, а с
`--execute` обучает отдельного кандидата и проверяет его. Действующая модель
не заменяется автоматически. Для запуска используется существующий `auto_ml.py`.

Это механизм обработки отчётов, а не сборщик обратной связи из API. Сервис пока
не записывает правильные пользовательские метки и не создаёт такие отчёты сам.
Потребуются разметка новых загрузок и внешний запуск команды после обновления
отчётов. Планировщик в системе и новые автоматизации Codex не устанавливались.

## Условия запуска

Стартовые настройки в `retraining_policy.json`:

- Падение macro-F1 более чем на 0,03 относительно базового периода **или**
  recall любого класса более чем на 0,10.
- Не менее 30 проверенных изображений каждого класса в каждом периоде.
- Только отчёты с проверенными метками и подтверждённой независимостью данных
  от обучения. Статусы являются утверждением проверяющего, не доказательством инструмента.
- Одна версия весов и кода inference; текущий отчёт должен быть новее базового.
- Не более одного запуска обучения за 24 часа; на одном наборе и версии модели
  повторная попытка автоматически не запускается даже после ошибки.

Метрики пересчитываются по `predictions`, а не берутся на доверии из полей
`metrics`. Проверяются хеши, классы, дубликаты, ошибки обработки и размер выборки.
Пороговые значения — начальные настройки. Они не являются статистическим тестом
значимости и требуют настройки под реальную частоту загрузок и стоимость ошибок.

## Подготовка отчётов

Для каждого периода нужна случайная выборка реальных загрузок с проверенными
категориями в структуре ImageFolder. Периоды должны иметь согласованную методику
отбора. Отдельно проверяйте смещение состава классов и разметки: падение метрики
само по себе не устанавливает причину ухудшения.

1. Разметить изображения и проверить их происхождение/пересечения с train.
2. Выполнить оценку с `evaluate_model.py --per-class 0` на полном периоде.
3. Подготовить metadata с отпечатком набора, проверяющим и описанием происхождения.
4. Повторить оценку с `--metadata`, чтобы отчёт содержал подтверждённые статусы.

Структура metadata описана в [MODEL_METRICS.md](MODEL_METRICS.md).
Старые диагностические отчёты без проверенных меток не запускают обучение.
Базовый отчёт не обновляется автоматически: иначе постепенное ухудшение
может стать незаметным. После смены модели требуется новый базовый период.

## Проверка без обучения

```bash
poetry run python retrain_on_degradation.py \
  --baseline reports/baseline_reviewed.json \
  --current reports/current_reviewed.json
```

Имена отчётов — пример: эти проверенные отчёты ещё нужно подготовить.
Команда сохраняет `reports/retraining_decision.json`. Состояние `stable` означает,
что падение не превышает пороги; `retraining_recommended` — что обнаружен триггер.
Без `--execute` веса не обучаются и очередь запусков не создаётся.

## Обучение при выполнении условий

```bash
poetry run python retrain_on_degradation.py \
  --baseline reports/baseline_reviewed.json \
  --current reports/current_reviewed.json \
  --model model_checkpoint.pth \
  --train-data my_dataset/retraining \
  --train-metadata reports/training_data_review.json \
  --evaluation-data my_dataset/current_reviewed \
  --execute
```

Обучающий набор должен содержать исправленные/проверенные изображения и все классы.
В него нельзя включать изображения из базового и текущего проверочных периодов.
Перед обучением сравниваются SHA-256 файлов. Визуально похожие кадры, серии
и разные размеры одного снимка необходимо исключить при ручной подготовке.
Состав наборов на время запуска нужно зафиксировать.

Метаданные train:

```json
{
  "dataset_sha256": "отпечаток полного обучающего набора",
  "label_review_status": "reviewed",
  "reviewer": "имя проверившего разметку"
}
```

Отпечаток можно получить через функции `scan_images` и `dataset_fingerprint`
модуля `retrain_on_degradation`. Заполнение статуса reviewed допустимо только
после реальной проверки данных. До обучения проверяется и точное совпадение
проверочной папки с текущим отчётом.

По умолчанию бюджет — 3 Optuna trials по 2 эпохи и 5 эпох финального обучения.
Флаги `--trials`, `--tuning-epochs`, `--final-epochs` задают положительные значения.
Обучение использует текущую схему ResNet18 с предобученными весами torchvision,
а не продолжает оптимизацию действующего legacy-checkpoint. При первом запуске
может потребоваться скачивание исходных предобученных весов.

## Результаты и защита от циклов

В `retraining_runs/<run-id>/` сохраняются кандидат `candidate.pth`, отчёт его
проверки, контекст запуска, лог оценки и результат. В `state.json` фиксируются
попытки, в том числе ошибки. Каталог исключён из Git; его нужно сохранять между
запусками и включать в резервное копирование, если он используется на сервере.

Состояния:

| Статус | Значение |
|---|---|
| `stable` | Падение ниже порогов |
| `retraining_recommended` | Есть триггер, обучение не разрешено флагом |
| `candidate_ready` | Кандидат улучшился и ожидает ручной проверки |
| `candidate_not_improved` | Улучшение не удовлетворяет условиям |
| `already_processed` | На этом наборе и версии модели уже была попытка |
| `cooldown` | Пауза между попытками ещё не истекла |
| `already_running` | Другая команда уже выполняет обучение |
| `blocked_or_failed` | Ошибка данных, конфигурации или обучения |

Кандидат проверяется на том же текущем holdout, что действующая модель.
Для рекомендации по умолчанию нужен прирост macro-F1 не менее 0,01 и отсутствие
ухудшения recall любого класса. Этот holdout не используется Optuna или обучением.
Проверка кандидата — ориентир для ручного решения; при многократной разработке
моделей нужен дополнительный нетронутый тест, чтобы не подстроиться под holdout.

Никакого автоматического копирования в `model_checkpoint.pth`, рестарта API или
деплоя нет. Код возврата 0 означает завершённую проверку, включая предупреждения
и пропущенные запуски; 2 — ошибку/блокировку. Решение читается из JSON.
Повторять неудачное обучение бесконечно система не будет. Для нового запуска
нужны новый набор после разбора причины и истечение cooldown.

Механизм использует файловую блокировку `fcntl` и рассчитан на Linux/macOS.

## CI

Проверки качества кода, тесты и сборка Docker остаются в CI. Блокирующая job
`model-metrics` и абсолютные пороги перед деплоем удалены. Само обучение на PR
не запускается. Проверки поведения триггера, ограничений запусков и сохранности
рабочих весов выполняются unit-тестами.

## Получение новых примеров из обратной связи

Включите согласие на сбор в форме загрузки и подтвердите или исправьте категории.
Сервис сохраняет копии и явные пользовательские метки в `feedback_data/feedback.sqlite3`
(путь задаёт `FEEDBACK_DIR`; в Docker используется постоянный том).
Без согласия копия не сохраняется. Исправление не перемещает файл в Nextcloud.

```bash
.venv/bin/python scripts/export_feedback.py \
  --output feedback_candidates/batch-001 \
  --exclude my_dataset/train \
  --exclude my_dataset/test_candidates
```

Добавьте через `--exclude` все контрольные и базовые наборы. Выходной каталог
должен быть новым. Сборщик исключает точные дубликаты и конфликтующие метки.
Похожие кадры и правильность меток проверяет человек; статусы выгрузки остаются
`unreviewed` и `unverified`. После проверки подготовьте отдельные train/holdout
и metadata по инструкции выше. Автоматическое расписание не установлено.
